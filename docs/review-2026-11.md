> **Status:** the fixes from this review are on branch `review-fixes`, and what is left is tracked in [`review-checklist.md`](review-checklist.md). This document is kept as written, as the reference behind each checklist item.

Reviewed at commit `35a996b` (2026-11-10) on Windows 11, Node 24, Obsidian 1.12.7. No source file was changed.

How findings were checked:

- **Build and lint:** `npm run build` passes; `npm run lint` gives 0 errors and 4 warnings.
- **Unit tests:** 335 of 336 pass on this Windows checkout. The one failure is a line-ending problem in the fixtures (finding B15), not a product bug.
- **Model bugs:** reproduced with a throwaway script that imports `src/model` and `src/store`.
- **View bugs:** reproduced in the real app, started with `scripts/launchObsidian.ps1` and driven over CDP. The files I created in the test vault were deleted afterwards.

Labels: **confirmed (app)** = reproduced in Obsidian; **confirmed (script)** = reproduced against the model; **confirmed (trace)** = followed through the code line by line, not executed; **suspected** = plausible, not proven.

## 1. The product and where it stands

Patchwork is a layout document for Obsidian. A `.patchwork` file (JSON, millimetres) holds fixed-size pages on a pan/zoom board. Pages hold modules that point at vault content: note sections, cropped PDF regions, images, plus free text, shapes, a table of contents, linked text frames and trackers. The author's use is D&D: put a spell list, a stat block and a rulebook crop side by side, have them follow edits to the source notes, print them as A4/Letter PDF or PNG, and use the same file at the table as a dashboard (Use mode).

Status against SPEC §11:

| Milestone | Status |
|---|---|
| M0 foundations, M1 editing, M2 export | Done. One spec item has no UI: manual page order. |
| M3 navigation and performance | Done (outline picker, PDF search, saved views, minimap, previews). |
| M4 print polish | Done (dark PDF, ink saver, booklet, bleed, masters, TOC, freeze, stale-PDF warning). |
| M5 advanced | Done (linked frames, trackers). |
| After the spec | Use mode, tints, shapes, in-place editing, automatic ink, context bar and popover. |

The spec's "Next" and "Later" lists are used up, so there is no written roadmap. 99 of the 105 commits are from 19–20 October; the code is wide and young. The model layer is clean and well tested. The weak spots are where features meet each other (frames × duplicate/move/masters, rename × undo, popout windows × theming/export), and almost all view logic sits in one 1 936-line class.

## 2. Bugs and risks, most severe first

### B1. Popout windows: invisible text and a silently empty export. Confirmed (app).

- `src/main.ts:89,92`: `refreshPaperScope()` installs the light-paper rule only in `activeDocument` at load and on `css-change`. A patchwork moved to a popout window has no rule in its document. Measured in the app, dark theme: paper `rgb(255,255,255)`, note text `oklch(1 …)`, so white text on white paper.
- `src/export/printHost.ts:186` builds the print host in `activeDocument` (the popout), while `src/export/printAdapter.ts:32` prints `getCurrentWebContents()` of the main window. Exporting the same page gave 72 KB from the main window and 4.8 KB from the popout: only the vector PDF region, no notes, no error.
- **Fix:** keep a paper-scope sheet per document (install it when a view opens, from `containerEl.doc`). For export, either build the host in the main window's document always, or print the web contents of the window that holds the host. Until then, refuse to export from a popout with a clear message.

### B2. Linked-frame chains break on move, duplicate and page duplicate. Confirmed (script).

- **Drag a middle frame to another page:** `BoardViewport.ts:1408` calls `moveModuleToPage` (`pageOps.ts:118–122`), which is `removeModule` + `addModule`. `removeModule` (`pageOps.ts:60`) re-links the follower to the removed frame's source, then the frame is added back still pointing at that source. Result: `n ← f2` and `n ← f1`; the moved frame shows "Another frame already continues the same text."
- **Duplicate a page** (`pageOps.ts:99–104`): modules get new IDs but `from` keeps the old ones, so every copied frame points into the original chain and shows the same error. The copied head note is not chained at all.
- **Duplicate a frame** (`pageOps.ts:91`): the copy has the same `from`; same error.
- **Fix:** move without the re-link (remove and add in one step, keep `from`). In `duplicatePage`, map `from` through the old→new ID table. For a duplicated frame, append it to the end of the chain or make it a text box with the shown text. Add these three cases to `tests/store/pageOps.test.ts`, which today only covers deletion.

### B3. A second conflict in the same minute loses the user's edits. Confirmed (trace).

- `conflictCopyName` has minute resolution and `PatchworkView.ts:157` uses `vault.create`, which throws when the file exists.
- In `setViewData` (`PatchworkView.ts:65`) the call is `void`-ed, so the rejection is swallowed and the edits are gone. In `saveNow` (`:138–140`) the disk version is loaded first, then the copy is attempted; if it throws, our version is already torn down.
- Scenario: Sync or git writes the file twice within a minute while there are unsaved edits (a pull that touches the file twice, or two devices).
- **Fix:** write the copy before loading the disk version; pick a free name (`… (conflict 2026-11-13 1015) 2`); on any failure keep the store and show a notice with "Copy my version".

### B4. A vault rename is an undo step on open boards. Confirmed (trace).

- `linkTracker.ts:29` applies the path rewrite with `store.update`. The next Ctrl+Z on that board, meant to undo a move, restores the old path and the module shows "Note not found". Older snapshots in the history also keep the dead path, so undoing further brings it back again.
- **Fix:** `BoardStore.updateOutsideHistory` already exists and maps a change over past and future. Use it for renames.

### B5. Picking a section by heading takes the first heading with that name. Confirmed (trace).

- `ui/pickers.ts:34` stores `#Heading` only. A bestiary note with `## Goblin / ### Actions` and `## Orc / ### Actions`: picking the Orc's Actions stores `#Actions`, which Obsidian resolves to the Goblin's. The spec (5.3) allows `#Parent#Child`.
- The same picker feeds the Section dropdown in the popover and "Pick another…".
- **Fix:** build the full path from the heading stack when the name is not unique in the note (or always).

### B6. "Export to canvas" overwrites an existing canvas without asking. Confirmed (trace).

- `BoardViewport.ts:828–831`: the target is the patchwork's name with `.canvas`, and an existing file is replaced with `vault.modify`. A user who keeps `DM screen.canvas` next to `DM screen.patchwork` loses the canvas. The PDF/PNG export warns about replacing; this path does not.
- **Fix:** ask, or write `Name (patchwork).canvas`.

### B7. Images and PDF embeds do not follow changes to their file. Confirmed (app) for images, (trace) for embeds.

- `ModuleHost.ts:104–108`: re-render is triggered by `metadataCache.changed` (markdown only) and by `pdfDocs.invalidate`, which returns early when the path is not an open PDF document (`pdfSource.ts:195`). An image module therefore never sees a `modify`. In the app, replacing the image file left the old picture on the board until the page was unmounted.
- A PDF embedded in a note (`![[book.pdf#page=2]]`) releases its document after drawing; 15 s later the document is dropped, and from then on a change to the PDF triggers nothing.
- **Fix:** on `vault.modify`, call `sourceChanged(file.path)` for every file, and keep the PDF invalidation as a side effect.

### B8. Linked frames on a master page do not work on the pages that use it. Confirmed (script, model level).

- `masters.ts:37` gives inherited modules new IDs (`page~module`) but leaves `from` pointing at the master's own IDs. `flowChains` knows nothing about the inherited IDs, so on every using page the frame shows "This frame isn't linked to any text" and the head note shows its whole text. The export reports the placeholder as a problem.
- **Fix:** in `resolvePage`, rewrite `from` with the same prefix, and let `flowChains` run on the resolved page; or state in the UI that masters cannot hold frames and block it.

### B9. Two exports can run at once. Suspected.

- `BoardViewport.ts:842` has no guard. A second export started from the command palette while the first is rendering puts two `.print` hosts in the document; `printToPDF` prints both, the page count check in `assemble` trips and vector regions land on the wrong pages.
- **Fix:** one export at a time per window (a module-level promise), with "An export is already running".

### B10. Undo does surprising things in three places. Confirmed (trace).

- **Use mode:** `BoardViewport.ts:1465` keeps Ctrl+Z active. A ticked checkbox in a note module is written to the note, not the store, so Ctrl+Z after it undoes the last Arrange edit instead (a module jumps back while "nothing can move").
- **Export:** `BoardViewport.ts:845` stores the dialog's choices with `store.update`, so the first Ctrl+Z after an export undoes export settings and appears to do nothing.
- **Coalescing has no time limit:** `nudge:` (`:1525`) and `scroll:` (`:1186`) groups stay open until another edit or a pointer-up. Nudge five times, come back ten minutes later, nudge again: one undo step.
- **Fix:** in Use mode, limit undo to edits made since entering it (remember the history length at the switch); use `updateOutsideHistory` for export choices; close a coalescing group after about a second of quiet.

### B11. Space-to-pan sticks after losing focus. Confirmed (trace).

- `BoardViewport.ts:1452` sets `spaceHeld` on keydown and clears it only on keyup on the board. Hold Space, Alt+Tab, release: every click pans until Space is pressed again. There is no `blur` handler.

### B12. PDF search results can mix two searches. Confirmed (trace).

- `CropModal.ts:149`: each run empties the list and awaits `searchPdf`, which cannot be cancelled. Enter twice with different terms on a 400-page rulebook: the first search finishes later and appends its hits under the second term's status line. Closing the modal leaves the search running until the document is destroyed.
- **Fix:** a run counter checked after the `await`, and an abort flag passed to `searchPdf`.

### B13. Shape modules bypass the serializer. Confirmed (script).

- `serialize.ts:18` has no `shape` entry, so `moduleOut` (`:73`) writes shapes "verbatim" like an unknown type. Float noise is not removed (`"x": 0.30000000000000004` next to a text box's `0.3`), and key order follows whatever the code built. Snapped drags hide it; Alt-drags and endpoint drags will churn diffs.
- **Fix:** add `shape: ['shape', 'fill', 'stroke', 'radius', 'p1', 'p2', 'startHead', 'endHead']` and tidy `stroke`.

### B15. Tooling on Windows

- **One unit test fails** on a default Windows checkout: `tests/sources/noteSlice.test.ts` "takes a line range relative to the section". `core.autocrlf=true` checks the fixture `test-vault/Rules/Combat.md` out with CRLF, and the test expects LF. There is no `.gitattributes`. **Fix:** `* text=auto eol=lf` (binary for `*.pdf`, `*.png`).
- After `npm ci`, Vitest did not start: `@rolldown/binding-win32-x64-msvc` was in the lockfile but not installed (npm's optional-dependency bug). Installing that one package fixed it. It may be specific to this machine; worth a second try on a clean clone before believing it.
- CI runs on Ubuntu only, so neither would show there.

## 3. Rule and spec drift

**Hard rules.** No violation found in the rules that guard data:

- `src/model/` has no `obsidian` import and no DOM use (rule 5).
- Lengths in the file are millimetres; the exceptions are deliberate fractions (crop, line endpoints) and the saved view's zoom (rule 4).
- A file that fails to parse is never written, in the view or by rename tracking (rule 2).
- Electron is touched in `printAdapter.ts` only; the PDF.js asset URLs are in `pdfSource.ts` only, with the reason stated (rule 6).

Rule 3 (unknown keys) holds for every path I traced. One soft spot: `itemsFromText` rebuilds checklist items whose text changed as `{ text }`, dropping unknown keys on those items.

Rule 9 (unmount, release, cancel) holds for module content. The gaps are B12 (search not cancellable) and the masters row in B14.

## 4. Performance and maintainability

**Performance.** The measured numbers in `docs/perf.md` look right for pan and open, and I found no unbounded cache: bitmaps have an LRU budget, thumbnails 32 MB, flow layouts 32 entries, undo 200 snapshots with structural sharing. What is not measured:

- **Dragging on a large board.** Every pointer move is a `store.update`, and every store change runs `BoardViewport.render()` (`:241`): all pages (`resolvePage`, ink, `PageElement.update`, furniture), labels, minimap, outline panel, popover, then `ModuleHost.sync()` over the visible modules with `setCssProps` on each. It is O(pages) per move, plus `masterOf`'s linear search inside `pageFurniture` (O(pages²) when masters are used). Probably fine at 100 pages, but the stress probe only measures panning. Add a "drag one module for 240 frames" probe before optimising.
- **Renames.** `onVaultRename` (`linkTracker.ts:13–19`) runs per renamed file, and each run filters `vault.getFiles()` twice and does a `cachedRead` of every closed board. Moving a folder of 500 notes in a 10 000-file vault is about ten million filter steps. Batch the events of one move (debounce) and compute `moved` once.
- **Saves.** `saveNow` serializes the board three times per write (`getViewData` before the read, inside `super.save`, and for the `unsaved` check). Cache the string per store snapshot.
- **Hidden masters** render in Use mode (B14).

**Maintainability:**

- **`BoardViewport.ts` is 1 936 lines** and owns camera, input state machine, selection, snapping, every "add" flow, export, saved views, menus and the toolbar. It is the file every feature touches, and it has no unit tests (`tests/view` covers `camera` only). Split by responsibility, not by size: `boardInput.ts` (pointer and key state machine, testable with a fake store), `boardActions.ts` (add, duplicate, delete, freeze, export; no DOM), `boardToolbar.ts`, `boardMenus.ts`. Do this before adding table-play features, or they will all land in the same class.
- **`PropertiesForm.ts` (552) and `ContextBar.ts` (583)** each describe the controls for each module type separately. A per-type descriptor (field, label, kind, where it shows) would feed both and the right-click menu.
- **Module type knowledge is spread over eight places:** `schema`, `validate`, `serialize`, `ModuleHost.CONTENT_KEYS`, `createRenderer` (twice: board and print host), `ContextBar`, `PropertiesForm`, `canvasExport`. B13 is exactly a missed place. A registry entry per type (keys, content keys, renderer factory, print renderer) would make "add a module type" one file plus forms. The spec already names `modules/registry`.
- **Tests.** The model is well covered (336 tests). Not covered by unit tests: `linkTracker`, the save/conflict flow in `PatchworkView` beyond `decideSave`, `ModuleHost`, `liveContent`, `InlineEdit`. They are covered by e2e only, which needs a running Obsidian and does not run in CI. The frame bugs in B2 would have been caught by four more lines in `pageOps.test.ts`.
- **Lint warnings worth acting on:** the settings tab does not implement `getSettingDefinitions()`, so Patchwork's settings are missing from Obsidian's settings search (1.13+).

## 6. UX walkthrough

Walked in the real app: new patchwork → note section → PDF crop → arrange → Use → export. Dark theme, 1 024 × 800 window.

**Create.**

- There is no ribbon icon. The ways in are the command "New patchwork" and the folder right-click menu. Add a ribbon icon and a "New patchwork" entry in the file explorer's new-file area.
- The new board is one white A4 page under an icon-only toolbar (at this width the labels collapse). Nothing says what to do. **Empty state:** on a page with no modules show, in the paper, "Drag a note, PDF or image here · or use Note / PDF above", gone after the first module.
- The status bar shows "62 words 756 characters": the word count of the JSON. Harmless, but it looks like a bug.

**Add a note section.** Three steps: Note button, pick the file, pick the section. The section step is good (indented headings, back arrow). Problems: the result fills the page (see tweaks), and identical heading names go wrong (B5). Dragging a note from the explorer skips the section step and places the whole note; hold a modifier, or show the section menu right after the drop.

**Add a PDF crop.** PDF button, pick the file, crop dialog, Apply: four steps, fine. The dialog is where time goes on a real book (no page field, no zoom). "Resize module to the crop shape" is on by default, which is right.

**Arrange.** Drag, snap, guides and resize all behave. Missing basics a user will reach for:

- **Copy and paste** (Ctrl+C / Ctrl+V), within a page, across pages and across patchworks. Only Ctrl+D exists.
- Paste text → text box; paste an image → image module.
- `Esc` to deselect; `Tab` to step through modules.
- Hotkeys shown anywhere: there is no cheat sheet, and the README list is the only place Space, Alt and Shift are explained. Add a "Keyboard and mouse" entry to the View menu.

**Use mode at the table.**

- The switch is the first control on the toolbar and the look is right: app theme, faint page, no chrome.
- At zoom-to-fit an A4 page on a laptop is about 52 %, so body text is around 6 px. A dashboard needs **"fit width" and page-to-page keys** (PageDown / PageUp, Home), and number keys for saved views. Today the only navigation is panning and the outline.
- Tracker buttons are too small at that zoom, and there is no typing (see tweaks).
- Links open to the side and reuse the pane: good. A hover preview needs Ctrl; fine.
- Nothing shows that the mode is saved in the file. Reopening a dashboard in Use is the right behaviour, but a first-time user who closes in Use and reopens will look for the toolbar. Keep the mode switch labelled ("Arrange | Use") even when the rest of the toolbar is compact.

**Export.**

- The dialog is clear, the defaults are right, and the warning "already exists and will be replaced" is good. One A4 page took 1.1 s.
- The problems list after export is useful ("the text doesn't fit its box and is cut off"). Make each problem clickable to select the module.
- Problems arrive as a sticky notice in the corner. For a long list, a small results dialog with the file link and the problems reads better.

**Error messages and themes.** Placeholders name the file and offer "Pick another…": good. The error view for a broken file is good. Dark and light themes work in the main window; a popout window does not (B1).

**F1. Rollable tables.** Problem: random encounters, loot and wild magic are tables in notes; rolling means a dice app plus finding the row.

- **Step 1, no new data:** in Use mode, a rendered markdown table whose first column header is a die (`d6`, `d20`, `d100`) or whose first column holds ranges (`1–3`) gets a small die button. Click: roll, highlight the row, show the result in a notice. Nothing is saved.
- Pure code: `model/dice.ts` (parse `NdM+K`, roll with an injected random source) and `model/rollTable.ts` (rows and ranges from table cells). The click handler goes next to the checkbox handler in `liveContent.ts`.
- Also in step 1: inline code `` `dice: 2d6+3` `` in text becomes clickable.
- Export: unchanged; the table prints as a table.
- Risks: the Dice Roller plugin uses the same inline syntax; skip elements it has already replaced. Ranges written with en dashes, `00` for 100.

**F2. Tracker upgrade.** Problem: HP and spell slots are the trackers used every round, and they are the weakest part of Use mode.

- Model, all optional, in `model/tracker.ts`: `resetTo?: number`, `group?: string` (for example `"short rest"`, `"long rest"`, `"encounter"`). Pure functions `applyInput(m, "-12")`, `reset(m)`, `resetGroup(file, group)`.
- UI: click the value to type; Shift-click steps by 5; a command and a button module "Reset: long rest".
- Export: as today (`printBlank`).
- Risk: resets across many trackers should be one undo step.

**F3. Use-mode navigation.** Problem: the dashboard is readable only zoomed in, and moving between pages by panning is slow mid-combat.

- No file change, except optionally `view.key?: 1–9` on saved views.
- PageDown / PageUp move to the next and previous page in output order at fit-width; `0` fits all; digits jump to saved views; `F` toggles Obsidian's full-screen for the pane.
- Pure: `camera.fitWidth`, `nextPage(file, currentId)`.
- Risk: keys must not fire while typing in plugin content (the guard at `BoardViewport.ts:1450` already handles this).

**F4. Templates.** Problem: a blank A4 is a slow start, and a second character sheet should start from the first.

- "New patchwork from template…": lists `.patchwork` files in a template folder (plugin setting) plus three built-ins made by pure functions in `model/templates.ts`: a DM screen (A4 landscape, three columns of empty note slots), a character dashboard (trackers for HP, slots, conditions checklist, note slots) and a spell-card sheet (nine 63 × 88 mm cards on A4 with crop marks).
- Needs an "empty slot" state: a note module with `file: ""` renders "Drop a note here" instead of "Note not found". Schema-compatible.
- "Save as template" copies the file, clears `frozen`, tracker values and `board.mode`.
- Export: slots print empty. Risk: none against D1–D10.

**F5. Copy and paste.** Clipboard text `{"patchwork":1,"modules":[…]}`; paste re-IDs and offsets, at the pointer if it is over a page. Plain text becomes a text box; an image is saved to the attachment folder and becomes an image module; `[[Note#Heading]]` becomes a note module. Pure: `pageOps.pasteModules` (re-ID, remap `from` inside the pasted set: the same remap B2 needs).

**F6. Quick add.** Problem: adding "the Fireball spell" is Note → file → section; a monster from a rulebook is PDF → file → find the page.

- One fuzzy dialog over note names, headings (`Spell list › Fireball`) and PDF bookmarks (`Rulebook › Goblin, p. 187`). Enter places a module in the first free slot of the page in view, sized to content.
- Pure: `model/placement.ts`, a free-slot finder generalised from `placeNextFrame`.
- PDF bookmarks are read lazily and cached in memory per file and mtime. No file-format change.
- Risk: vaults with thousands of headings; build the index on first open and update on `metadataCache.changed`.

**F7. Pages from notes.** Problem: spell cards and monster cards are the same layout repeated for 30 notes.

- Command "Pages from notes…": choose a folder or tag, a page (the pattern) and which note module on it is the slot. It creates one page per note by duplicating the pattern and pointing the slot at each note.
- One-shot generation, with `page.generatedFrom?: { pattern: string; source: string }` so "Refresh generated pages" can add and remove pages later. Everything else is existing model.
- Export: nothing new; with a spell-card sheet as the output sheet, existing tiling and crop marks apply.
- Risk: this is the closest thing to pagination in the list. It stays inside D3 because every card is a fixed page and nothing flows between them. Do not let it grow into "split a long note across cards".

**F8. Encounter tracker.** Problem: initiative order, HP and conditions for six creatures is the DM's main bookkeeping.

```ts
interface EncounterModule extends BaseModule {
  type: 'encounter';
  rows: { id: string; name: string; init?: number; hp?: number; maxHp?: number;
          ac?: number; conditions?: string[]; link?: string; side?: 'party' | 'foe' }[];
  turn?: string;        // row id
  round?: number;
  printBlank?: boolean; // export: names and empty boxes
}
```

- Pure `model/encounter.ts`: `sorted`, `nextTurn`, `damage`, `toggleCondition`, `addFromNote(name, frontmatter)` (reads `hp`, `ac`, `init` if present).
- UI in Use mode: Next turn (also a key), click HP to type a delta, condition chips, the name links to its note (opens to the side).
- Export: a table; blank with `printBlank`, for pencil play.
- Risks: scope creep toward a rules engine; keep it a table with arithmetic. Every click is a save and an undo step; coalesce per row. Size L because of the UI, not the model.

**F9. Visibility flags.** `BaseModule.hide?: ('export' | 'use')[]`. A tracker that should not print, a GM note that should not show on the dashboard, a "cut here" guide that should only print. Pure filter in `exportPlan` and in `ModuleHost.sync`; the outline shows a dimmed row. Small, and it removes the need for separate "print" and "play" copies of a board.

**F10. Smart crop.** In the crop editor: zoom (wheel), a page field, and "crop to block": cluster the PDF.js text items around the click and set the crop to their bounds plus a margin. Pure clustering in `model/pdfGeometry.ts`. No file change.

**F11. Roll module with history.** Only if F1 gets used and the history is missed.

```ts
interface RollModule extends BaseModule {
  type: 'roll';
  dice?: string;                                   // "1d20"; default from the table
  table?: { file: string; subpath?: string } | { rows: { range: [number, number]; text: string }[] };
  history?: { at: string; roll: number; text: string }[];   // newest first, capped (10)
  printBlank?: boolean;                            // export without history
}
```

- Export prints the table and, unless `printBlank`, the last results.
- Risk: history in the file makes every roll a save, and with Sync a possible conflict copy mid-session. Write it outside the undo history and cap it.

**F12. Peek.** In Use mode, a plain click on an internal link opens the note as a floating card over the board (Obsidian's hover popover, pinned) instead of a split. The layout does not shift mid-game; Ctrl+click still opens to the side. A per-board choice: `board.linkOpen?: 'side' | 'peek'`.

**F13. Find.** Ctrl+F: search module labels, text boxes, note sources and page names; Enter cycles and reveals. Pure search over the model, plus the text of mounted notes.

**F14. Player view.** A second window showing one saved view, read-only, without modules flagged `hide: ['players']`. Needs popout windows to work first (B1), and F9.

**What D6 costs.** A table dashboard is a natural tablet use. Use mode makes the desktop-only decision more expensive than it was when it was taken. Not arguing to reverse it; worth knowing when weighing F3 and F8, which are both better with touch-sized targets anyway.
